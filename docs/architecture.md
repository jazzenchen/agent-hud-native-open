# Architecture

## Overview

Agent HUD Open is a Swift package with three libraries and one executable. `AgentHUDCore` reads agent activity and account usage on this Mac and normalizes it into a `UsageReport`; `AgentHUDDesktop` presents that report in the menu bar, the notch and the settings and statistics windows; the standalone application wires the two together. A host application can embed the libraries, supply its own provider, add settings pages, and relay the island's alerts. Account services, synchronization and any relay of alerts are outside the package.

## Model

| Module | Responsibility | Depends on |
| --- | --- | --- |
| `AgentHUDSupport` | `JSONValue` (integer-preserving JSON) and `RecordCoding` (deterministic encoding, millisecond dates, hashed identities) | — |
| `AgentHUDCore` | Providers, usage models, calculations, alert decisions, the usage ledger, the settings and usage stores, the hover panel's layout and the MCP server | Support |
| `AgentHUDDesktop` | Menu bar item, notch glow and panel, island alerts, onboarding, settings and statistics windows; its resource bundle holds every logo and notice | Core |
| `AgentHUDOpenApp` (product `AgentHUDOpen`) | Launch options, live or sample data, adapter setup, process lifetime | Desktop, Core |

`CombinedUsageProvider` reads one provider per client, one after another, and merges their reports; `UsageLedger` is the local SQLite store where providers keep parse positions, token events and quota readings, and from which the 15-minute usage and cost totals are read; `RetainedUsageProvider` restores the saved report at start and fills readings a partial refresh could not supply; `UsageCollector` runs the collection pipeline: it waits for sources to signal new data, reads the signalled sources and runs account steps one at a time, and hands each report to `UsageStore`, which publishes the report the desktop observes. A report carries quota windows, sessions with their token breakdown, turns, completions, 15-minute usage buckets, services, billing and the account inventory (`ProviderAccount`, `AccountObservation`); every quota row belongs to one account.

## Rules

### Host integration

- A host creates a `SettingsStore` and a `UsageStore` around any `UsageProvider`, then a `DesktopApplication`; it owns every additional service and its lifecycle. The shared UI never initializes account services or transports.
- A host supplies `additionalHUDControls` beside the expanded HUD's Stats button. Its factory receives an action that collapses that display's HUD before opening another window; the host owns the controls' state and calls that action before presenting its window. `additionalMenuItems` adds host entries below Settings.
- A host hands its process arguments to `HookEntry.handle(arguments:)` first thing at launch: the clients' hook commands and the adapter commands run there and quit without the interface, the `--mcp` server once its client closes its input, a hook's flag or client the build does not know quits quietly, and anything else starts the application. A host with `--…-hook` commands of its own runs them before handing its arguments over, or they would quit quietly here.
- `UsageAssembly` builds the settings and the store as the standalone application does, over the installed clients with the restart copy on screen, or over the sample data without a ledger, with the host's collection hooks; `UsageProbe.run(settings:)` prints the `--probe` diagnostics.
- `fetchUsage(agents:historyHours:)` assembles local activity with the latest account results; `refreshAccountUsage(historyHours:)` performs the slower quota, balance and account-wide requests at every call and has a no-op default, and the collector alone spaces those calls; `accountRefreshSteps` splits it into steps the store runs between reads, and `watchedDirectories` names the directories whose changes need a read (nil means the provider is read every poll interval). A provider that wraps another forwards all of them.
- `sources` splits a provider into parts read on their own, each with its signals: its directories, its account steps and the checks it asks for. A provider that does not split itself is one source. `fetchUsage(agents:historyHours:sources:)` reads the named sources again and keeps every other source's last result, and `sourceChecks()` names the times at which a source's last result changes with time alone. `accountChecks(since:spread:now:)` names when each source's account steps are next worth running, a scheduled reading waiting the spread the collector drew for it, and `seesLocalWork` is false for a provider whose usage is the account's from every device, which keeps it on the account interval. `CombinedUsageProvider` makes one source per vendor.
- A provider that does not write the ledger reports its periods in `UsageReport.usage`; `CombinedUsageProvider` adds them to the ledger's totals.
- Notices are reported by vendor in `UsageReport.sourceNotices`. A provider says what went wrong with a reading as a `ReadingIssue`, a failed read or an account it could not confirm, at the scope where it read: the vendor's in `readingIssues`, which alone hold back the vendor's alerts, levels, reset credits, retained sessions and Codex window inventory; one account's or plan pool's in `AccountObservation.readingIssue`, which holds back that account's rows; a balance's in `APIBilling.readingIssue`. A notice about local logs or hooks is shown and holds nothing back. A billing pool and its rows answer to their pool's issue alone, never to the vendor's, since each pool is read on its own. Each issue's reason is also written as notice text (`quotaNotices`, `AccountObservation.quotaNotice`, `APIBilling.notice`), and a report without typed issues counts that text as failed reads, or every source notice when it has no `quotaNotices`.
- `UsageReport.status(of:)` gives the status of a window's, an account's or a balance's reading: a window and an account answer to the account's issue, else the vendor's. `assess(_:now:)` adds whether its account is current, its age and its reset. The rows' levels, quota alerts, reset credits, retention and the account headers ask it.
- A failed full refresh keeps the previous report on screen and exposes `UsageStore.lastError`, which the store's view passes to `ReportView` so that every reading of that report counts as failed; a partial failure keeps the missing readings from the saved report.
- `DesktopApplication` decides and presents island alerts itself: one `IslandEventTracker` checks every change of the report, the agent list or the Live status preference while the store is neither paused nor failing, and the island shows the new quota events, added usage resets and completed turns. Every host, the standalone application included, gets the same alerts without extra wiring.
- A host that relays alerts elsewhere passes `onIslandEvents`. It receives every check after the island has presented it, including checks that found nothing, with the report and time the check used; the host maps that update and never runs a second tracker or presents again.
- Completions in an update already honor `Settings.liveStatusEnabled(for:)`; hosts apply the same preference in any other relay or synchronization service they add ([session lifecycle](session-lifecycle.md)).
- A client's prompt and Stop hooks give no turn of their own: a session's phase comes from its log, which a host that receives those hooks has read at once ([hooks remind](session-lifecycle.md#hooks-remind)).

### Collection signals

- A source is read only when it signals new data: a file change under its directories, a log under them a host reminded the collector of, its account step finishing, one of its checks falling due, or, for a source without directories, its poll interval. Whatever a source does inside, whether it watches files, receives hook callbacks or polls a service, the collector sees only these signals. A host can also ask for a pass that reads a source by a time.
- Reads stay serial: signals only mark sources as due, and the collector reads the due sources in one pass; signals that arrive during a pass are read by the next one, and passes start at most every `UsageRefresh.readSpacing`, except one that reads a log a host reminded the collector of.
- Time-based changes of activity are checks, not polls: a session whose source never said what its turn is doing is read again when it reaches `SessionPhase.Limits.quiet` without an observation, and a running turn when it stops counting as current work and again at `SessionPhase.Limits.abandoned`, where silence means its client is gone.
- File events name real paths; the collector compares them with each directory as given and as `realpath` resolves it.
- A source's account steps run when its own work, or one of its windows resetting, makes a new reading worth taking; opening the panel, the menu or the statistics window reads every account, and no source repeats a request within `UsageRefresh.accountRequestSpacing`.
- A settings change that needs a read wakes the collector at once, through `SettingsStore.onChange`, which a running `UsageStore` sets: a changed agent list reads every source, and GitHub Copilot quota reading switched on or off reads Copilot's quota at once, within the request spacing too, and every other account the spacing allows. The pass it wakes is serial like any other. `CombinedUsageProvider.standard(settings:ledger:persistent:)` takes the same `SettingsStore`, and the Copilot provider asks it for the consent whenever a reading is due.
- Every source is read again every `UsageRefresh.accountInterval`, which catches a file event the watch missed, and a refresh reads every source once.
- A host whose clients' hooks say something happened in a session's log, such as a prompt submitted or a turn stopped, reminds the collector of it (`UsageStore.remind(paths:)`). The reminder is read by the next pass, as a file event would be, without waiting for the read spacing or for the event itself, which a log written through an open handle may never give; a pass under way leaves it to the next one. The log is then looked at three more times, half a second apart, and read again whenever it changed, for what its client writes right after the hook (`LogReminders`). A reminder carries nothing the store keeps.
- A host that reads something of its own in `afterPass` and needs a pass by a time that no file event may bring, such as a transcript it put off until then, asks for one (`UsageStore.requestPass(for:at:)`). The sources that own the paths it names are read at the first pass at or after that time, or at the next pass when it gives no time, within the read spacing like any pass. Nothing changed, so the provider is told of no change, `afterPass` is named none of the paths, and nothing is looked at again after it (`PassRequests`); a path no watched source owns has every source read.

### Collection hooks

- A host passes `UsageCollectionHooks` to `UsageStore`; every hook is optional, and without them the store displays the provider's report and loads `UsageStore.historyHours` hours, the seven-day range plus the partial hour.
- `historyHours` is asked before every local poll and account step, so a host can widen the window providers read tokens for. It does not widen the sessions: a provider builds sessions only for those active within `SessionWindow.recency`, seven days, each with its whole sub-agent tree, and reports the turns and completions of those sessions and trees.
- `publish` receives each report the provider returned. It is awaited inside the pass, after the provider fetch and before the report is displayed; no provider reads and nothing writes the ledger meanwhile, so a hook that reads the ledger stays serial with collection.
- `afterPass` runs after each read, once the store shows its report, with the paths under the sources' directories that changed since the read before: those the file watch reported, the recent logs found grown and the reminded logs. They are nil when the collector cannot name them: at the first read, after events the watch dropped, while nothing can be watched, at the fallback read of every source and after the agent list changed. The pass, and so the next one, waits for it, so what a host reads there, such as the transcripts of the sessions that changed, stays serial with collection.

### Session observers and hooks

- `SessionObservers.configure(executable:enabled:)`, called after creating the store and before `start()` with `Settings.clientHooks`, installs the Pi and OpenCode observers when those clients' directories exist, the Antigravity, Cursor, GitHub Copilot CLI, CodeBuddy and Qwen Code stop hooks, Claude Code's notification and compaction hooks and each detected client's approval hook when those clients are installed, or with `enabled` false removes Agent HUD's handlers from them. Creating a `DesktopApplication` installs nothing; a change of `clientHooks` while it runs applies at once with the main bundle's executable, and while `clientHooks` is on, an observer directory that appears after launch (`SessionObservers.observedClients()`) gets its observer at the next report (`SessionObservers.installObservers()`).
- Every Agent HUD handler belongs to the copy that runs, since only one runs at a time: `configure` points each one at the executable it is given, whichever copy wrote it, and adds none from under App Translocation or `/Volumes` ([completion hooks](session-lifecycle.md#completion-hooks)).
- `HookSettings.write(_:to:)` writes every client settings file the hooks change, and a host's own hooks can use it too: through a symbolic link to the file it leads to, keeping the file's permissions.
- `HookInstaller` reads one hook's settings file, up to 16 MB, and points Agent HUD's handlers in it at the running copy or takes them out, the hook's own edit given; `HookCommand` makes and recognizes a handler's command. A host's own hooks use both.
- `UnixSocketListener` is the application's end of the socket a hook process reaches through `UnixSocket`: only the user can reach it, a request is one message the sender ends by closing its side, and one process serves a path.

### Panel layout and agent tools

- `SettingsStore.panelLayout` is the hover panel's `PanelLayoutStore`: a shared layout and, by screen key (`ScreenIdentity.key(for:)`), any screen's own, each with its saved layout, the one saved before it and an unsaved draft. A screen's panel and resting HUD draw `effective(for:)`: the screen's own layout, draft first, where it has one, else the shared layout's, with no mixing of the two. A screen's draft can also be to use the shared layout (`PanelScreenLayout.shared`). The saved layouts are one value in the store's defaults, `panelLayout.v2` (`PanelLayoutStorage`), and drafts live in memory; `revision` counts every document's changes as one number. `SettingsStore.onChange` hears nothing of the layouts, so a change of them never wakes collection.
- The store also holds each screen's style draft (`HUDStyle`), an agent's change to that screen's placement and glow, held in memory and never stored. `SettingsStore.effectivePlacement(on:hasNotch:)` and `effectiveGlow(on:)` draw it over the settings, and every place the HUD reads a screen's placement or glow reads those: `ScreenIdentity.placement(for:in:)`, `ScreenHUD`, the glow's appearance, `IslandController.panelScreens` and the Settings previews. `IslandController`'s inputs carry each screen's style draft and panel width, so a change re-applies that screen's HUD on the path a change of the settings takes. The store writes the settings only for a person's Save, Revert to Previous or HUD style Reset to Default of a screen (`resetLook(_:)`), through the `SettingsStore` that owns it, with one `update`; a screen's version keeps its placement and glow before (`previousLook`, `previousStyle` in `panelLayout.v2`), so `revert(_:)` undoes the layout's `reset(_:)`, which leaves the look, and `resetLook(_:)`, which leaves the layout, alike. `set_panel_layout`'s `from` `previous` for an attached screen proposes that version's look with its layout (`proposePrevious(_:hasNotch:)`), and `hud.reset` the default look (`proposeDefaultLook(for:hasNotch:)`), each as a style draft that lists the fields that differ and holds the look whole (`PanelStyleDraft.restoring`), which the screen draws and Save writes back as it was kept; `from` `default` proposes the default layout alone (`proposeDefault(_:)`). `SettingsStore.updateScreen(_:_:)` is a person's edit of one screen: it drops that screen's style draft first, and `ScreenHUD.beginMoving(at:)` drops it as a drag begins.
- A screen's look, its `appearance` (`HUDAppearance`) and `material` (`HUDMaterial`), is part of its `ScreenPlacement`, so the style draft, Save, Discard, Revert to Previous and both resets carry it as they carry the rest of the placement. `SettingsStore.effectiveLook(on:)` in AgentHUDDesktop is the one place a screen's `HUDLook` comes from, for `ScreenHUD`, the pictures and the Settings previews: the placement in effect, `SystemAppearance.isLight` for `system`, never the app's Appearance, and `NSWorkspace`'s Reduce Transparency, which draws glass solid; it carries the transparency of the material drawn, `glassTransparency` or `solidTransparency`, none under Reduce Transparency. At a hardware notch `ScreenHUD.islandLook(open:)` draws the island in the notch row's dark (`HUDLook.inNotchRow`) until it opens, and `SettingsStore.restingLook(on:)` gives the pictures and previews of the resting HUD the standard look there, black as the island at rest is (`NotchInk`). With Match screen on (`Settings.appearanceFollowsScreen`, a switch beside `appearance`) `WindowLook` gives every `HostedWindowController` and the status menu the look of their screen's HUD (`SettingsStore.windowLook(on:)`), refreshed by `DesktopApplication` when the settings, the displays, macOS's light or dark setting or Reduce Transparency change, and by a window that changes screen. `IslandController` re-applies every HUD, with the HUD's motion, when macOS turns light or dark and when the accessibility display options change, and its inputs already carry the settings and the style drafts.
- A layout's `hud.agents` says which agents its screen's resting HUD shows. `HUDAgentOrder` resolves it against what the HUD would show now, matching by `VendorMark.key`, and narrows nothing when it names none of them. `ScreenAgents` applies it in the HUD: `ScreenHUD`'s Dynamic queue, Simple items and glow parts, pulse vendors and pace come from it, and `IslandController`'s inputs carry each screen's list, so a change, a draft included, re-applies the closed HUD. The menu bar, the alerts, the requests and the store's own lists read the store as it is.
- `PanelLayoutPlan(layout:blocks:contentWidth:pairs:)` resolves a layout against `ReportView.panelBlocks`, the blocks the panel has now. What a layout names that does not exist is passed over and stays in the document, and a widget, a measure, a hidden countdown, columns, a ring size or half a line a block does not take falls back to the block's default. A stored layout is read that way; a proposal is not: `PanelTools` refuses one that asks for anything the panel cannot do, naming every mismatch, except what a layout already holds for a block or a row that is away.
- The plan also sets the blocks in `lines`: two blocks next to each other in its order that both take half a line share one where each half, half of `contentWidth` less the spacing's gap (`PanelSpacing.blockGap`), is at least `PanelLines.narrowestHalf`, 230 pt, the room `widestHeading` measures for the longest agent name's heading; every other block, a lone half among them, takes the whole line, and `PanelBlockPlan.span` and `columns` say how each is set (two cells to a line in half of one, a layout's columns kept up to what leaves each cell at least `PanelLines.narrowestCell`). The width is the content's, inside the display's insets: `HoverPanelView` works it out from the width the island gives it (`width(_:insets:)`) and passes `pairs: false` on one agent's own panel, and `PanelTools` takes it from the host's `PanelFit.contentWidth`, or beside the notch at the layout's width where the host gives none. Pairing depends on nothing but the plan, so a fresh view tree measures the height the island opens to, and a pair draws in `PanelHalves`, a `Layout` that gives each half the same width and the line the taller one's height, sets each view in the half its `PanelHalves.Side` names, so a half fading over to another block takes the same half while both are drawn, and that a balance's card in half a line also sets its two columns with, so `ViewThatFits` weighs them as drawn, under the `panelHalf` environment value, which the half blocks' headings and rows read.
- The plan also carries the layout's session and token filters, `PanelSessionFilter` and `PanelTokenFilter`. `ReportView.panelSessions(_:vendor:)` chooses the session rows from the view's sessions with set operations alone, an agent's own panel's vendor applied first, and gives what `get_panel` counts too; no project is resolved and the ledger is not read. The token chart's columns for a period and a set of models come from `UsageStore.hudTokenColumns(consumerIDs:period:)`, built once for each report and interval end and kept in the store beside the view (`hudColumns(_:end:build:)`), since a panel body is evaluated on every pass; `panelTokenConsumers(_:vendor:)` joins the layout's agents with an agent's own panel's. The chart keeps its period as state, starting from the layout's, and is handed its models on every pass, so a model that joins while the panel is open is drawn with the next report: the island measures the panel on a fresh view tree, which starts from that period, and the chart is as tall in every period, so a flip never changes the height it measured.
- A client's agent reaches the application through the `--mcp` process ([command line](command-line.md#mcp-server)). The process answers the protocol itself and passes on only tool calls, one connection a call, to `MCPAppChannel`: a `UnixSocketListener` on `mcp.sock` in the data directory. `DesktopApplication.start()` answers the channel with `PanelTools`, and `AgentToolsChannel` opens and closes it with `Settings.agentTools`, the switch in Settings → Experimental, off by default; a demo launched with `--demo-tools` (`DesktopLaunchOptions.demoTools`) serves it whatever the switch says and one without never does, since a demo shares the data directory with the real copy and one process serves the socket. A call that finds no socket served is told the tools are off when `InstanceLock.runningApplication(at:)` names a copy of the application that keeps its data in the same directory, and that Agent HUD is not running otherwise.
- Tool calls answer from held state: the last report, the settings and the layout store. The handler runs for any process of this user that reaches the socket, so it never starts a provider read, opens the panel or writes the agent list or the settings, and it keeps nothing a person did not confirm: a proposal is a draft, and only `PanelLayoutStore.save()`, behind the panel's Save button, keeps one.
- The panel's views and the screens are AgentHUDDesktop's, so `PanelTools` is handed four closures for them. `screens` lists the attached displays as `PanelScreen`s (`IslandController.panelScreens`): key, role, mode and edge in effect, notch and the agents each resting HUD can show now in each mode, by vendor, and whether macOS is light and Reduce Transparency is on, from which `get_panel` and the pictures' notes work out the look each screen draws with the same rule as the HUD (`ScreenPlacement.drawsLight(hasNotch:systemIsLight:)`, `drawsGlass(hasNotch:reducesTransparency:)`). `hud` draws one screen's resting HUD for `get_panel_image` with show `hud`; `DesktopApplication` passes `HUDPictureRenderer`'s, which draws the Settings preview of that screen, its style draft included, in a hosting view that is never put in a window, the glow as a still frame. `picture` and `fit` take the scope asked for; `DesktopApplication` passes `PanelPictureRenderer`'s, set to that screen's layout, at the width the island gives it (`HoverPanelView.width(_:insets:)`, which widens a side dock's panel to keep its content at least 404 pt), and island (`ScreenHUD.panelDisplay`, worked out from the placement in effect, so a style draft just proposed is measured as it will show), the main display's for the shared layout: `picture()` draws the `HoverPanelView` in a hosting view that is never put in a window, with the `masksIdentity` environment value on, which `AccountSectionHeader` and the session rows read, and under which `redactedOnPicture()` draws a reading's reason or a client's notice as placeholder bars; `fit()` measures it with `IslandWindowController.naturalHeight(of:)`, the path the island measures its panel with before opening, and gives the width its content is laid out in, which decides where `get_panel` says two halves share a line. A host without them gets no `height` in `get_panel` and a refused `get_panel_image`. The picture reaches the process in `MCPToolReply.result(_:images:)`, written as `"images"` beside the result on the channel, and the server hands each one on as an image block.

### Client declarations

- Every client Agent HUD reads or hears from is an `AgentClient`, and `ClientDeclarations` holds one `ClientDeclaration` for each: the channels through which its sessions, its usage, each phase of its sessions and each kind of request it asks arrive, with the answers the HUD can send back and how a request answered in the client itself is noticed. A part a client does not offer is empty, and nothing is inferred for it.
- A channel is the client running a hook, an event of the plugin or extension Agent HUD adds, a subscription the client sends changes on, what a log or table gained since a saved position, an answer asked for at a stated interval where nothing can be observed, or a whole file or table read again at every change. The last is below the baseline every client is moving to, and `belowBaseline` lists where a client still reads that way.
- The declarations describe what is read today and change with it; tests hold them to the hooks installed, the observers that run and the readers each provider uses.

### Storage

- The standalone bundle identifier is `app.agenthud.open`; preferences live in its UserDefaults domain, with separate domains for demo and snapshot runs.
- The usage ledger, the restart copy of the report (including account labels), hashed Kimi identities and completion records live in the data directory ([storage](providers.md#storage)); token events keep 31 days, quota readings 30 days and API balance readings one day. No file contains credentials, and the only conversation text in them is a session's title, which can be the first line of its first prompt, 60 characters at most.
- SwiftPM resources are located through `AppResources`; the app bundle carries `AgentHUDOpen_AgentHUDDesktop.bundle` under `Contents/Resources`.

### Design invariants

- Integer precision: whole numbers decode as `Int64` before `Double`; token counts are never rounded or interpolated.
- Deterministic identities: record ids are SHA-256 hashes of length-prefixed components, identical on every machine.
- Millisecond dates: persisted dates round-trip through milliseconds since 1970.
- Tests need no credentials or network; the only probe that touches installed clients is opt-in.
- Isolated sources: a missing, signed-out or failing client never hides another.
- One copy at a time: every application built on these libraries shares `InstanceLock`, whatever its data directory or bundle identifier. A host calls `SingleInstance.claim()` at launch, after its probes and before it opens preferences, the ledger or a client's settings, and quits when it returns false.
- No invented lifecycle: inactivity is never a completion, and a passed reset deadline is not a confirmed reset.
- Observed rows only: quota windows and accounts come from provider readings, never from a built-in placeholder list; Settings lists every source supplied by the host alongside reported rows and services. Groups for undetected sources follow all other groups, preserving relative order within each section and existing windows' manual order.
- Settings groups a provider's windows by their existing display account identity, names each account once and uses each window's compact name; dragging a window reorders its account's existing HUD slots without moving another account's windows.
- Names apart from ids: vendor ids key settings, the ledger, accounts and sync records and never change; `VendorCatalog` holds the names shown, and a value it does not name is shown as written, never filed under another.
- Resources and notices: the root `THIRD_PARTY_NOTICES.txt` and the bundled copy stay byte-identical, and source comments cite the file.
- Source boundaries: `make check` rejects signing material, private service directories and imports, secret-shaped strings, external package dependencies, missing ignore rules and a bundled notices file that differs from the root one.

### Versioning

- A release is a tag `vX.Y.Z` on `main`; the bundle's `CFBundleShortVersionString` equals `X.Y.Z` at that tag, `CFBundleVersion` stays `1`, and the [changelog](../CHANGELOG.md) has a matching entry that lists host-visible API changes. Hosts pin the package by tag or commit.
- There are no third-party Swift package dependencies; frameworks come from the macOS SDK.
- Continuous integration runs the boundary check, `swift test`, a release build, `codesign --verify --deep --strict`, a check that the resource bundle contains the logos, a check that no provisioning profile was embedded and one that the executable names the SDK it was built against, not its deployment target, within 30 minutes. It publishes no binaries.
